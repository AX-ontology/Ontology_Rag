Methodology / Catalog-first pipeline

업무는 하나로 묶고,
근거는 그대로 남깁니다.

문서마다 표현이 달라도 같은 업무라면 기존 TaskFrame에 먼저 통합합니다. 범위 밖의 업무만 새로 만들고, 전체 문서의 근거를 모아 PCF 후보를 연결합니다.

자이제 1·2·3 통합 결과 탐색 ↗
01 / END-TO-END

추출 → 기존 업무 직접 배정 → 전체 근거 PCF → 검증

실행 진입점: run_all.bash → run_catalog_pipeline.py · catalog-pipeline-3.0-direct

생성형 LLM 기본 2단계 + 신규가 있을 때만 1단계

01 — EXTRACT / LLM

문장에서 근거 추출

업무 언급(TaskMention), 주어–관계–목적어 삼중항(Fact), 페이지·문장 근거를 추출합니다. 임시 TaskFrame 생성·재통합은 생략합니다.

02 — DIRECT ASSIGN / LLM

기존 업무에 직접 배정

추출한 업무 언급을 승인 목록에 바로 배정하고, 같은 요청에서 애매한 Fact 연결도 원문 문맥으로 판단합니다. 기존 ID와 정의는 유지합니다.

03 — NOVEL ONLY / CONDITIONAL LLM

신규가 있을 때만 묶기

NOVEL 언급만 큰 업무로 묶습니다. 기존·앞서 생성한 신규 목록을 함께 참조합니다. 별도 최종 목록 검토 호출과 상하위 업무 생성은 없습니다.

04 — CONNECT & VERIFY

PCF 연결과 검증

문서별 근거를 합쳐 PCF를 한 번 계산합니다. 정제·보존·연결 검증 후, 명시적으로 요청한 경우에만 Neo4j에 적재합니다.

기존 C001…에 배정 → 재사용같은 업무 범위면 기존 TaskFrame ID에 언급·Fact를 연결합니다.
NOVEL → 신규 묶음 생성기존 범위 밖이라는 근거가 있는 후보만 새 업무 생성 단계로 보냅니다.
REVIEW → 검토 후 재개업무 배정·Fact 연결이 불확실하면 검토 목록을 남기고 중단합니다. 임의 배정·강제 연결은 하지 않습니다.

2~3단계는 API 호출 2~3회를 뜻하지 않습니다. 기본 언급 48개/배치, Fact 최대 160개/요청이며 오류 재요청·캐시·입력량에 따라 실제 호출 수가 달라집니다. 비용 감소율은 아직 측정하지 않았습니다. PCF는 로컬 BGE 임베딩·reranker를 사용하고, 정제·DB·HTML은 생성형 API를 사용하지 않습니다.

02 / HISTORICAL RESULTS

기존 결과의 584개와 12개

아래 수치는 단순화 이전에 완료·승인한 결과입니다. 584개는 자이제2 내부의 임시 후보 수이며 기존 12개 중 11개 업무에 배정됐습니다. 새 직접 배정 경로에서는 이 임시 후보 생성 단계를 거치지 않습니다.

문서정렬 전사용한 공통 업무신규

문서별 업무 수는 겹치므로 더하지 않습니다. 전체 업무는 합집합 12개입니다. 업무 언급과 Fact는 업무 통합 후에도 보존합니다.

03 / IDENTITY & PROVENANCE

이름을 묶어도 원문은 잃지 않게

TaskMention → MEMBER_OF → TaskFrame

TaskFrame → HAS_*_FACT → Fact

Fact → SUPPORTED_BY → EvidenceSpan

Fact 연결은 핵심·보조·맥락으로 나뉩니다. 하나의 Fact가 여러 업무를 뒷받침할 수 있으므로 업무별 Fact 수의 합은 전체 고유 Fact 수와 다를 수 있습니다.

업무 계층은 만들지 않습니다. 그래프의 CHILD_OF는 PCF 분류체계의 계층이며 TaskFrame 상하위 구조가 아닙니다.

04 / CONTROL POINTS

자동 처리와 검토의 경계

오류·재실행 안전장치

입력 별칭 S001…과 기준 업무 C001…을 분리합니다. 응답이 잘못되면 정상 배정은 보존하고 오류 항목만 재판정합니다. 반복 실패는 숨기지 않습니다.

입력·설정·코드 해시로 완료 산출물을 재사용합니다. 원문이 바뀌면 추출과 배정을 다시 수행하고, 기준 문서가 바뀌면 기준 목록 재검토가 필요합니다.

구조 검증 ≠ 의미 정확도

ID·관계 무결성과 원본 보존 통과가 추출 내용의 정확성을 보증하지는 않습니다. 격리된 Fact도 근거 추적을 위해 남으며 활성 지식으로 취급하면 안 됩니다.

PCF 후보 점수는 모델·검색의 판단 점수이지 정답 확률이 아닙니다. 업무 배정 승인과 PCF 연결 확정은 별개의 절차입니다.

현재 자이제1·2·3 결과는 이미 승인한 추출·배정을 재사용한 것입니다. 이후 새 문서에 적용되는 existing-first 전략과 과거 배정 결과의 생성 이력을 동일한 것으로 해석하지 않습니다. 자이제2의 낮은 신뢰 배정 55개는 사용자 승인에 따라 유지했습니다.
05 / RUN

하나의 진입점으로 실행

cd /path/to/AX_ontology/Ontology/final_pipeline
# 계획만 확인
bash run_all.bash --dry-run
# 추출 → 공통 업무 → PCF → 정제 → 검증
bash run_all.bash
# 검증 결과를 실제 DB에도 적재할 때만
bash run_all.bash --load-neo4j

기준은 config.yaml의 승인된 목록 파일입니다. DB의 모든 과거 업무를 자동으로 기준 목록에 넣지는 않습니다.

06 / REPRODUCE

결과 위치와 읽는 방법

current.json 실제 단계별 결과 경로

catalog_pipeline_manifest.json 실행·재사용·DB 검증 이력

combined/taskframes.json 전체 문서의 공통 업무 및 구성원

validation_report.json 노드·관계·보존 검증

이 HTML은 로컬 산출물에서 만든 고정 스냅샷입니다. API 호출·DB 쓰기·외부 리소스 없이 열립니다. 결과가 바뀌면 보고서 생성기를 다시 실행하세요.
